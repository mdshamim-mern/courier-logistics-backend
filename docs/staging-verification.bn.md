# পরীক্ষামূলক পরিবেশের যাচাই

তারিখ: ৮ অক্টোবর ২০২৬।

## তথ্যভান্ডার ও সমন্বিত পরীক্ষা

স্থানীয় গোপন পরিবেশ-ফাইলের `STAGING_DATABASE_URL` ব্যবহার করে `20261008000000_security_payment_attempts` মাইগ্রেশন প্রয়োগ হয়েছে। `User.tokenVersion`, `Shipment.courierEarning` ও `PaymentAttempt`-এর উপস্থিতি আলাদাভাবে যাচাই হয়েছে। প্রকৃত পরীক্ষামূলক ডেটাবেসের কাঠামো ও বর্তমান Prisma কাঠামোর মধ্যে অমিল পাওয়া যায়নি।

একই পরীক্ষামূলক PostgreSQL-এ আলাদা, এলোমেলো পরিচয়ের অস্থায়ী স্কিমায় আটটি পরীক্ষা চালানো হয়েছে। সবগুলো সফল; সময় প্রায় ১২১.৪ সেকেন্ড। শেষে শুধু সেই স্কিমাটি সরানো হয়েছে। বিদ্যমান ব্যবহারকারীর রেকর্ড মুছে দেওয়া হয়নি। Redis-এর সব তথ্য পরিষ্কার করা হয়নি; পরীক্ষার নিজের সেশন-কী বাতিল করা হয়েছে।

সমন্বিত পরীক্ষায় Stripe ঘটনার তথ্য কৃত্রিমভাবে তৈরি হয়; এটি প্রদানকারীর কাছ থেকে আসা প্রকৃত বিজ্ঞপ্তি নয়। PostgreSQL ও Redis সংযোগ প্রকৃত পরীক্ষামূলক সেবায় হয়েছে।

## পরীক্ষায় পাওয়া সংশোধন

দূরের ডেটাবেসে পূর্বনির্ধারিত পাঁচ সেকেন্ডের লেনদেনসীমা অতিক্রম করায় প্রথমে তিনটি পরীক্ষা ব্যর্থ হয়। লেনদেনের অপেক্ষাসীমা ও চলার সময়সীমা যাচাইকৃত কনফিগারেশনে নেওয়া হয়েছে। অপেক্ষার পূর্বনির্ধারিত সীমা দশ সেকেন্ড এবং লেনদেনের সীমা বিশ সেকেন্ড। সর্বোচ্চ অনুমোদিত সীমা যথাক্রমে ত্রিশ ও ষাট সেকেন্ড।

একই অর্থপ্রদানের চেষ্টায় সমসাময়িক সফলতার লগ পুনরাবৃত্ত হওয়াও ধরা পড়ে। এখন সফল অবস্থা লেখার আগে শর্তযুক্ত পরিবর্তন দিয়ে একটি অনুরোধই চেষ্টাটি দাবি করতে পারে। সরাসরি SQL-এর সারি-লকে কনফিগার করা স্কিমা স্পষ্টভাবে যুক্ত এবং পরিচয়-মান প্যারামিটার হিসেবে পাঠানো হয়। পার্সেল, অর্থপ্রদান ও প্রশাসকের কুরিয়ার পরিবর্তনে একই সহায়ক ব্যবহার হয়।

ছাব্বিশটি স্বতন্ত্র পরীক্ষা, টাইপ যাচাই, কোড যাচাই এবং উৎপাদন বিল্ড সফল। এই সংশোধনগুলি আলাদা `codex/staging-provider-verification` ব্রাঞ্চে; এগুলো মূল ব্রাঞ্চে স্বয়ংক্রিয়ভাবে মার্জ বা অ্যাপ হিসেবে প্রকাশ করা হয়নি।

## সরাসরি প্রদানকারী পরীক্ষার ফল

| সেবা | যাচাইকৃত ফল | যা এখনো যাচাই হয়নি |
| --- | --- | --- |
| Stripe | পরীক্ষামূলক API-তে ১২০ টাকা, BDT, সফল লেনদেন এবং প্রদানকারীর কাছ থেকে আবার পড়ে যাচাই | অ্যাপের Checkout নিষ্পত্তি ও বাইরে থেকে বিজ্ঞপ্তি পৌঁছানো |
| bKash | স্যান্ডবক্সে পরিচয় যাচাই, লেনদেন তৈরি ও Initiated অবস্থা; পরীক্ষার পাতায় প্রবেশ-ত্রুটি ও failure প্রত্যাবর্তন | সফল গ্রাহক অনুমোদন, execute ও Completed অবস্থা |
| ইমেইল | EMAIL_SENDER ঠিকানায় একটি পরীক্ষামূলক বার্তা; SMTP গ্রহণ করেছে, প্রত্যাখ্যান শূন্য | প্রাপকের ইনবক্সে পৌঁছানোর নিশ্চিতকরণ |
| ছবি | Cloudinary-তে স্বাক্ষরিত PNG আপলোড, HTTPS-এ ডাউনলোড ও ছবির বিষয়বস্তু যাচাই; নিজের পরীক্ষার ছবি সরানো হয়েছে | অ্যাপের প্রোফাইলে ছবি সংরক্ষণ ও সম্পূর্ণ ব্যবহারকারী-পথ |

Stripe-এর স্থানীয় স্বাক্ষর যাচাই সফল, কিন্তু নিজের গোপন মান দিয়ে পরীক্ষার স্বাক্ষর তৈরি করে যাচাই করাকে Stripe-এর প্রকৃত বিজ্ঞপ্তি পৌঁছানোর প্রমাণ ধরা হয়নি। সরাসরি পরীক্ষামূলক লেনদেনের পরিচয়: `pi_3UOEvQDpm6kSsUsI2oKwVnlQ`।

বর্তমান Stripe API-তে `payment_method_types` পাঠালে ত্রুটি এসেছে। পরীক্ষার স্ক্রিপ্টে সেটি সরিয়ে স্বয়ংক্রিয় অর্থপ্রদানের পদ্ধতি ও পুনর্নির্দেশ নিষিদ্ধ করার মান ব্যবহার করা হয়েছে। অ্যাপের মূল Checkout অনুরোধে ক্ষেত্রটি আগে থেকেই ছিল না। [Stripe-এর নির্দেশনা](https://support.stripe.com/questions/fix-the-payment-method-types-error)।

bKash-এর প্রথম সরাসরি পরীক্ষায় `TR0011EDErkPf1791456543256` লেনদেন তৈরি হয়েছে, কিন্তু গ্রাহক অনুমোদন বা execute হয়নি। গ্রাহক-অনুমোদনের প্রথম পরীক্ষা `TR0011UfdvaXl1791456826434`-এ প্রদানকারীর পাতায় `Invalid page access request` দেখা গেছে; প্রত্যাবর্তনের পরে প্রদানকারী তখনো Initiated বলেছে। নতুন পরীক্ষা `TR00117mokgWB1791457623023`-তেও failure প্রত্যাবর্তন এসেছে এবং প্রদানকারী Initiated বলেছে। দুই চেষ্টার স্থানীয় সহায়কই দশ মিনিটের সীমায় বন্ধ হয়েছে। Completed অবস্থা বা সফল অর্থপ্রদান পাওয়া যায়নি। শুধু পরীক্ষামূলক পাতা ব্যর্থ হওয়া থেকে শংসাপত্র বা OTP ভুল বলে নিশ্চিত সিদ্ধান্ত নেওয়া হয়নি। এই সহায়ক মূল অ্যাপের পেমেন্ট রেকর্ডে ফল সংরক্ষণ করে না।

পরবর্তী যাচাইয়ে bKash-এর স্যান্ডবক্স মার্চেন্টের উপযুক্ত পরীক্ষা-প্যাকেজ, অনুমোদিত প্রত্যাবর্তনের ঠিকানা এবং প্রদানকারীর ফেরত দেওয়া নতুন লিংক নিশ্চিত করতে হবে। কোনো ব্যক্তিগত OTP/PIN বা গোপন API মান চ্যাট বা গিটে পাঠানোর দরকার নেই। সম্পূর্ণ অ্যাপের অর্থপ্রদান ও বিজ্ঞপ্তি যাচাইয়ের জন্য প্রকাশ্য পরীক্ষামূলক ব্যাকএন্ডের ঠিকানা ও প্রদানকারীর বিজ্ঞপ্তি-সংযোগও দরকার।

বিকাশের নিজস্ব [Tokenized Checkout পরীক্ষার পাতায়](https://merchantdemo.sandbox.bka.sh/tokenized-checkout/version/v1.2.0-beta) প্রকাশ্য পরীক্ষার নম্বর `01770618575`, OTP `123456` এবং PIN `12121` দেওয়া আছে। এগুলো স্যান্ডবক্সের মান, কোনো প্রকৃত ব্যবহারকারীর গোপন কোড নয়। ওই পরীক্ষার নম্বরে নিজের ফোনে বার্তা পাওয়ার অপেক্ষা করার দরকার নেই।

## পুনরায় চালানোর নিয়ম

কাজের সম্পূর্ণ পথ:

D:\NEXT_LEVEL_WEB_DEV\assignment\courier-backend

গোপন মান গিটে নয়, নিজের `.env` ফাইলে রাখুন। স্বাধীন পরীক্ষার জন্য `STAGING_DATABASE_URL` এবং `INTEGRATION_REDIS_URL` প্রয়োজন। স্ক্রিপ্ট নিজের তৈরি স্কিমা ছাড়া সাধারণ স্কিমায় সমন্বিত পরীক্ষা চালায় না। একাধিক মাইগ্রেশন একই সময়ে চালাবেন না; প্রদানকারীর পুল করা সংযোগে মাইগ্রেশনের লক-সময়সীমা একবার দেখা গেছে। সম্ভব হলে মাইগ্রেশনের জন্য প্রদানকারীর সরাসরি সংযোগ ব্যবহার করুন।

```powershell
npm run test:staging
npm run test:providers -- --only stripe
npm run test:providers -- --only email
npm run test:providers -- --only image
npm run test:providers -- --only bkash
npm run test:bkash:interactive
```

সমস্ত প্রদানকারীর প্রাথমিক পরীক্ষা একসঙ্গে চালাতে `npm run test:providers`। এতে নিজের EMAIL_SENDER ঠিকানায় বাস্তব পরীক্ষামূলক ইমেইল যায়, পরীক্ষার ছবি আপলোড ও পরিষ্কার হয়, এবং স্যান্ডবক্সে লেনদেন তৈরি হয়। bKash-এর প্রাথমিক স্ক্রিপ্ট গ্রাহকের OTP বা PIN নিজে দেয় না; অসম্পূর্ণ অবস্থা সফল হিসেবে দেখায় না। এক সেবার পুনঃপরীক্ষায় `--only` ব্যবহার করুন, যাতে অন্য সেবায় অনুরোধ বা ইমেইল পুনরাবৃত্ত না হয়।

গ্রাহক-অনুমোদনের স্ক্রিপ্ট শুধু স্থানীয় HTTP প্রত্যাবর্তন ও bKash স্যান্ডবক্স গ্রহণ করে। শুধু পরীক্ষামূলক নম্বর ব্যবহার করুন; প্রকৃত মোবাইল হিসাব বা গোপন তথ্য চ্যাটে দেবেন না। অনুমোদনের পরে প্রদানকারীর execute ও অবস্থা পড়ে পরিচয়, পরিমাণ, মুদ্রা ও সফল অবস্থা মিলতে হবে। দশ মিনিটে অনুমোদন না হলে পরীক্ষা অসম্পূর্ণ থেকে বন্ধ হয়।
